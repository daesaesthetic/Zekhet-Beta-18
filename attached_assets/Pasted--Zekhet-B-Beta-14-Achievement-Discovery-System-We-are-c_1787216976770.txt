# Zekhet-B Beta 14 — Achievement & Discovery System

We are continuing development of Zekhet-B.

The current codebase is at Beta 13 and all existing systems are functioning correctly.

The following systems are confirmed to exist:

* Tuto system
* Tuto objectives
* Tuto page progression/unlocks
* Persistent user data
* Item definitions
* Persistent inventories
* Egyptian-themed item collection
* Currency/economy
* XP
* Levels
* Ranks
* Unified reward system
* `/profile`

This beta introduces the **Achievement & Discovery System**.

IMPORTANT:

Do NOT rebuild or replace any existing systems.

Achievements should use existing systems and the Unified Reward System rather than creating duplicate progression, XP, currency, item, or unlock logic.

---

# 1. CORE OBJECTIVE

Create a persistent achievement system that gives users optional long-term goals, milestones, and secrets to discover.

Achievements should complement the existing Tuto system rather than duplicate it.

The distinction should be:

**Tuto**

> Guided progression and learning.

**Achievements**

> Optional accomplishments, milestones, challenges, and discoveries.

A player should be able to complete the Tuto progression without needing every achievement.

Likewise, achievement hunters should have reasons to explore beyond the Tuto system.

---

# 2. ACHIEVEMENT DATA STRUCTURE

Create a centralized achievement definition system.

Each achievement should support:

* Unique ID
* Name
* Description
* Category
* Requirement/condition
* Reward
* Hidden/visible status
* Completion state
* Optional progress tracking
* Optional completion timestamp

Achievement definitions should be separate from individual user completion data.

Adding a new achievement should ideally require adding a definition rather than modifying the core achievement engine.

---

# 3. ACHIEVEMENT CATEGORIES

Create a flexible category system.

Initial categories can include:

### Progression

Achievements related to:

* Levels
* Ranks
* Tuto progression
* Major milestones

### Economy

Achievements related to:

* Earning currency
* Spending currency
* Reaching wealth milestones

### Collection

Achievements related to:

* Obtaining items
* Collecting unique items
* Obtaining rare items
* Obtaining legendary/mythic items

### Activity

Achievements related to:

* Using commands
* Completing actions
* Returning to the bot
* Completing repeated activities

### Discovery

Achievements related to:

* Finding hidden mechanics
* Triggering unusual interactions
* Discovering secrets
* Finding rare content

### Special

Achievements that do not fit the other categories.

The category architecture should remain extensible.

# 5. HIDDEN ACHIEVEMENTS

Hidden achievements should be a major feature of this system.

Some achievements should intentionally hide:

* Their name
* Their description
* Their requirement
* Their reward

Until the user discovers them.

Before discovery, present them mysteriously.

Example:

> 𓂀 **???**
>
> *Something beneath the sands has noticed you.*

After discovery:

> 𓂀 **THE WATCHER**
>
> *Discover something that was never meant to be found.*

The system must distinguish between:

* Hidden and undiscovered
* Hidden but discovered
* Visible and incomplete
* Completed

Do not reveal hidden requirements through `/achievements`.

---

# 6. DISCOVERY ACHIEVEMENTS

Create several achievements specifically designed around exploration.

Examples could involve:

* Using an unusual command
* Performing an unexpected sequence of actions
* Interacting with a specific item
* Finding a secret feature
* Triggering an unusual response
* Discovering something outside normal Tuto progression

Do not implement arbitrary or confusing requirements simply for the sake of secrecy.

Every hidden achievement should have a deliberate trigger.

Avoid making hidden achievements dependent on impossible or unknowable conditions.

---

# 7. AUTOMATIC ACHIEVEMENT DETECTION

Achievements should be checked automatically when relevant events occur.

For example:

User reaches Level 10.

The system detects:

> Achievement requirement satisfied.

It then automatically unlocks the achievement.

Users should NOT have to manually run `/achievements` to discover that they qualified.

Potential event sources include:

* XP gained
* Level reached
* Rank reached
* Currency gained
* Currency spent
* Item obtained
* Item used
* Tuto objective completed
* Tuto page completed
* Command executed
* Future gameplay events

Only connect to events that actually exist in the current codebase.

---

# 8. CENTRAL ACHIEVEMENT SERVICE

Create a reusable achievement service.

Conceptually it should support functionality such as:

* `checkAchievements(user, event)`
* `unlockAchievement(user, achievement)`
* `getAchievements(user)`
* `getAchievementProgress(user, achievement)`
* `hasAchievement(user, achievement)`

Use naming consistent with the existing codebase.

The achievement engine should not contain its own copies of XP, currency, inventory, or Tuto logic.

It should query or listen to the existing systems.

---

# 9. REWARD INTEGRATION

Achievements must use the existing Unified Reward System.

Do NOT create separate achievement reward logic.

An achievement may reward:

* XP
* Currency
* Items
* Existing unlocks
* Future compatible reward types

Example:

> 🏆 **ACHIEVEMENT UNLOCKED**
>
> **Relic Keeper**
>
> Obtain your first rare relic.
>
> **Rewards**
> ✦ +500 XP
> 𓏺 +250 Deben
> 𓆣 Nile Pearl ×1

The actual reward should come from the achievement definition.

---

# 10. ONE-TIME COMPLETION

Achievements must only be completed once per user.

The system must prevent:

* Duplicate completion
* Duplicate rewards
* Duplicate notifications

The backend must enforce this.

Do not rely solely on the UI.

---

# 11. PROGRESS-BASED ACHIEVEMENTS

Support achievements that require cumulative progress.

Examples:

> Earn 100,000 total currency.

> Collect 25 unique items.

> Complete 50 objectives.

> Use the bot 500 times.

The system should track progress where necessary.

Example:

> **Treasury**
>
> `72,450 / 100,000 Deben`
>
> ███████░░░

If an achievement has no meaningful partial progress, do not force a progress bar onto it.

# 16. EVENT-BASED ARCHITECTURE

Where possible, achievement detection should be connected to existing system events rather than manually inserted into every command.

For example:

**Item obtained**
↓
Achievement system checks relevant collection achievements.

**XP gained**
↓
Achievement system checks level/progression achievements.

**Tuto objective completed**
↓
Achievement system checks Tuto achievements.

This will make future systems easier to integrate.

Do not introduce a complicated event architecture if the current project does not need one.

Use the simplest architecture that remains extensible.

---

# 17. DATA SAFETY

Do not reset existing users.

Do not alter:

* XP
* Levels
* Ranks
* Currency
* Inventory
* Tuto progress
* Existing unlocks

Achievement data should be additive.

Existing users should automatically be eligible for achievements based on their existing state where practical.

For example:

If a user already reached Level 10 before the achievement system was implemented, they should be able to receive the Level 10 achievement when the system evaluates their existing state.

Do not require users to repeat previously completed actions unnecessarily.

---

# 18. INITIAL ACHIEVEMENT BALANCE

The initial achievement collection should have a healthy progression curve.

Aim for approximately:

* 30% easy/early
* 30% medium
* 20% difficult
* 20% hidden/secret

Do not make every achievement a grind.

Achievements should encourage players to explore different parts of Zekhet-B.

# 21. FINAL ARCHITECTURE

After this beta, the core progression architecture should look like:

**PLAYER ACTION**
↓
**Existing Game System**
↓
**Event / State Change**
↓
┌──────────────────────────────┐
│ Unified Reward System        │
│ Achievement System           │
└──────────────────────────────┘
↓
**XP / Currency / Items / Unlocks**
↓
**Level / Rank / Tuto / Achievements**
↓
**Profile / Inventory / UI**

The Achievement System should be an additional progression layer, not a replacement for Tuto.

The intended player experience is:

**Tuto tells the player what they can do.**

**Progression shows them how far they've come.**

**Achievements reward them for going beyond the expected path.**
